# Bug — `ripple init` never wires the MCP server / skill into the target project

Source: untracked `bug` note in repo root (2026-09-08).
Reviewed by software-architect — approved with 5 required + 8 recommended changes; all folded in below
(see **Review outcomes** at the end for the decisions taken on each).

## Context

After `ripple init` in a fresh directory the user gets `ripple.config.json` + `.env.example` and
nothing else. `src/commands/init.js` never touches `.mcp.json` or any `skills/ripple/SKILL.md`
copy, and `src/commands/mcp-setup.js` only runs `npm install` inside the package's own `mcp/`
folder and prints a `.mcp.json` snippet for the user to paste by hand. So Claude Code (and every
other supported host) has nothing telling it to launch `node mcp/src/index.js` or to load the
`/ripple` skill — the MCP server is unreachable from a project that used the documented setup path.

Two secondary defects surface once the primary one is fixed:

1. **The skill is not shipped.** `package.json#files` is `bin, src, mcp, README.md` — `skills/`
   is excluded, so an npm-installed ripple has no `SKILL.md` to copy even if `init` wanted to.
2. **The server's dependencies are not installed by `npm i -g ripple-qa`.** `mcp/package.json` is
   a separate, `private` manifest; npm does not install nested manifests, so `mcp/node_modules`
   does not exist on a fresh install and `mcp/src/index.js` fails at import time. Today that is
   what `mcp-setup`'s `npm install` works around — but nothing in `init` triggers it.

The repo's own copies (`.claude/skills/ripple/SKILL.md`, `.mcp.json`, …) are generated by
`scripts/sync-agents.mjs`, whose target lists are exactly the per-host paths a target project
needs. That script is dev tooling (not in `files`), so the lists must move somewhere shipped.

## Deliverable

After `ripple init` (or `ripple mcp-setup`) in any directory, restarting Claude Code / Copilot CLI /
Antigravity / OpenCode in that directory exposes the five `ripple__*` tools and the `/ripple`
skill, with no manual file editing. The repo's own generated copies keep being produced by
`npm run sync:agents` from the same target lists.

## Approach

### 1. `src/hosts.js` — shipped single source of truth for per-host paths

New module (lives in `src/` so it is packaged and importable from both the CLI and the sync script):

```js
export const SKILL_TARGETS = [
  '.claude/skills/ripple/SKILL.md',   // Claude Code (also read by GitHub Copilot CLI)
  '.agents/skills/ripple/SKILL.md',   // Antigravity CLI (also read by GitHub Copilot CLI)
  '.github/skills/ripple/SKILL.md',   // GitHub Copilot CLI primary
  '.opencode/skills/ripple/SKILL.md', // OpenCode
];
export const MCP_CONFIG_TARGETS = [
  '.mcp.json',               // Claude Code + GitHub Copilot CLI
  '.agents/mcp_config.json', // Antigravity CLI
];
```

Plus the writer:

```js
export function writeHostWiring(targetDir, { packageRoot } = {}) → { skillFiles, mcpConfigFiles, serverPath }
```

- `packageRoot` defaults to the installed ripple package root (`resolve(__dirname, '..')`).
- Skill: copies `<packageRoot>/skills/ripple/SKILL.md` byte-for-byte to every `SKILL_TARGETS`
  entry under `targetDir`, creating directories. Overwrites unconditionally — these are generated
  copies, same rule as the sync script. Throws a descriptive `Error` if the source is missing
  (broken install).
- MCP config: for each `MCP_CONFIG_TARGETS` entry, **merge** rather than clobber — read the
  existing file if present, parse, set `mcpServers.ripple`, write back with 2-space indent. Other
  servers the user has configured are preserved. An existing file that is not valid JSON throws
  `"<path> is not valid JSON — fix it or delete it and re-run ripple mcp-setup."` rather than
  leaking a `SyntaxError`.
- The `ripple` entry written is:

  ```json
  { "command": "node",
    "args": ["<abs>/mcp/src/index.js"],
    "env": { "RIPPLE_PROJECT_ROOT": "<abs targetDir>" } }
  ```

  Absolute paths are unavoidable: the server lives inside wherever npm put the package, which is
  machine-specific by nature. `RIPPLE_PROJECT_ROOT` is set explicitly because only Claude Code is
  known to spawn project-scoped servers with `cwd` = project; `mcp/src/env.js` already honours
  the variable (it `chdir`s), so this makes the server host-agnostic without relying on any
  host's cwd behaviour. Paths are normalised to forward slashes for readability on Windows
  (`node` accepts them). Consequence: the generated `.mcp.json` is per-machine; teammates
  regenerate it with `ripple mcp-setup` (documented in README and in the command's output).

### 2. `src/commands/mcp-setup.js` — actually write the wiring

- Split the existing `npmInstall` into `ensureMcpDeps()`: resolve
  `@modelcontextprotocol/sdk/package.json` via `createRequire(<mcp/src/index.js>)`; if it
  resolves, do nothing; else run the existing `npm install --omit=dev` in `mcp/`. Exported so
  `init` can reuse it.
- Then call `writeHostWiring(process.cwd())` and print each file written, followed by
  "Restart your Claude Code / Copilot CLI / Antigravity / OpenCode session, then run
  `/ripple analyze <KEY>`". The copy-paste snippet goes away.
- Command description in `bin/ripple.js` updated to say what it now does (one-line change; the
  v1 command surface is unchanged).

### 3. `src/commands/init.js` — wire by default

After `ripple.config.json` / `.env.example` are written, add one `confirm`:

> Set up /ripple for AI coding agents (Claude Code, Copilot CLI, Antigravity, OpenCode)? — writes
> .mcp.json and skill files here

default `true`. On yes: `await ensureMcpDeps()` then `writeHostWiring(process.cwd())`, print the
files, and add a "Restart your agent session and run `/ripple analyze <KEY>`" line to Next steps.
On no: print that `ripple mcp-setup` does it later. The prompt exists because CLI-only users
should not get four dot-directories dropped in their project unasked.

### 4. Packaging

- `package.json#files` gains `"skills"` so `SKILL.md` ships.
- `@modelcontextprotocol/sdk` and `zod` are added to the **root** `dependencies` (same ranges as
  `mcp/package.json`). Node resolves modules upward, so `mcp/src/*.js` finds them in the package
  root's `node_modules` on a fresh `npm i -g ripple-qa` — no runtime `npm install` into a
  possibly read-only global directory. `mcp/package.json` stays (standalone `cd mcp && npm i`
  still works for anyone running the server outside the CLI), and `ensureMcpDeps()` keeps the
  install as a fallback for a checkout where root deps were never installed.
- `scripts/sync-agents.mjs` imports `SKILL_TARGETS` / `MCP_CONFIG_TARGETS` from `src/hosts.js`
  instead of holding its own copies. It keeps writing the repo's *relative* `mcp/mcp-config.json`
  to the repo's own `.mcp.json` — that file must stay machine-independent because it is committed.

### 5. Docs / process files

- README: replace the (absent) MCP setup section with `ripple init` → restart → `/ripple`, plus
  `ripple mcp-setup` for re-wiring / teammates.
- CLAUDE.md v2 "Config and secrets" bullet about `.mcp.json` updated: the repo's own copy is
  relative; generated copies in user projects carry absolute paths + `RIPPLE_PROJECT_ROOT`.
- `issues.md`, `progress_logs.json`, `feature_list.json` entries.

## Test scenarios

**Unit / integration — `tests/host-wiring.test.js`** (node:test, temp dirs, same style as
`tests/config.test.js`):

1. `writeHostWiring(tmp)` creates every `SKILL_TARGETS` file byte-identical to
   `skills/ripple/SKILL.md`, and every `MCP_CONFIG_TARGETS` file with `mcpServers.ripple`
   whose `command` is `node`, whose `args[0]` is an absolute path to an existing file ending in
   `mcp/src/index.js`, and whose `env.RIPPLE_PROJECT_ROOT` resolves to `tmp`.
2. An existing `.mcp.json` with another server (`{"mcpServers":{"other":{…}}}`) keeps `other`
   after wiring; running `writeHostWiring` twice is idempotent (second run produces identical
   bytes).
3. An existing `.mcp.json` that is not JSON throws an `Error` whose message names the file and
   does not contain `SyntaxError`.
4. The target lists exported by `src/hosts.js` are the ones `scripts/sync-agents.mjs` uses —
   guarded by the script importing them (no separate test needed), and by the existing
   "byte-identical to their targets" check surviving a `npm run sync:agents` run.

**End-to-end — same file, real server process:**

5. From a temp project dir that contains a `.env` (`JIRA_API_TOKEN=x`) but **no**
   `ripple.config.json`, and with the test's own `cwd` left at the repo root: read the generated
   `.mcp.json`, spawn the server with the MCP SDK `Client` + `StdioClientTransport` using exactly
   `command`/`args`/`env` from the file, `listTools()` returns the five `ripple__*` names, and
   `callTool('ripple__get_ticket_context', { ticketId: 'KAN-1' })` returns the structured
   `CONFIG_ERROR` envelope (proving the server resolved the *temp* dir as project root — it found
   the temp `.env` and missed the temp config — not the cwd it was spawned from). No stack trace
   in the payload.

**Manual E2E** (recorded in Verification below): `node bin/ripple.js mcp-setup` in a scratch
directory, then `claude` there and confirm `/mcp` shows `ripple` connected with 5 tools.

## Review outcomes (software-architect, 2026-09-19)

Required — all adopted:

1. **Checkout guard.** `writeHostWiring` throws when `realpathSync(targetDir)` equals
   `realpathSync(packageRoot)`: the repo's committed `.mcp.json` / `.agents/mcp_config.json` are
   deliberately relative and are produced by `npm run sync:agents`, never by the runtime writer.
2. **Repo-copy sync test.** New `tests/host-sync.test.js` asserts every `SKILL_TARGETS` /
   `MCP_CONFIG_TARGETS` file in the repo is byte-identical to its canonical source, and that the
   committed `.mcp.json` contains no absolute path and no `RIPPLE_PROJECT_ROOT`. (The plan
   previously referenced a "byte-identical" test that did not exist.)
3. **Deps probe uses real specifiers.** `ensureMcpDeps({ mcpDir })` resolves
   `@modelcontextprotocol/sdk/server/mcp.js` and `zod` from `mcp/src/index.js` — the specifiers
   the server actually imports — not `…/package.json`, which only resolves by accident through
   the SDK's `./*` exports pattern. `mcpDir` is injectable so the probe is unit-testable.
4. **E2E test cannot pass vacuously.** The temp project gets a `ripple.config.json` with a
   sentinel invalid `github: { owner: 'sentinel' }` (no `repo`) plus `.env` with
   `JIRA_API_TOKEN=x`; the assertion is that `CONFIG_ERROR`'s message names `github.repo`.
   `loadConfig()` checks the env var before `applyGithubDefaults`, so reaching that message proves
   both temp files were read — a bare "no config" error could also come from the repo root, where
   `ripple.config.json` is gitignored. Client closed in `finally`.
5. **One zod instance in the dev checkout.** `tests/mcp-schema.test.js` imports bare `'zod'`;
   `mcp/node_modules` is removed from the checkout (root `node_modules` now serves `mcp/src`);
   `tests/host-sync.test.js` also pins `mcp/package.json`'s dependency ranges to the root's so
   they cannot drift. CLAUDE.md's Stack bullet is updated: root `dependencies` are authoritative,
   `mcp/package.json` mirrors them for standalone use.

Recommended — adopted:

6. `MCP_CONFIG_TARGETS` entries are `{ path, host, entry(serverPath, projectRoot) }` so a
   host-specific config shape is a one-line addition. Both current hosts use the Claude-Code
   shape (GitHub Copilot CLI reads `.mcp.json` in that shape for compatibility; its own
   `type`/`tools` keys belong to `~/.copilot/mcp-config.json`, which is not a project file).
7. Merge guards: 0-byte file → `{}`; missing `mcpServers` → created; `mcpServers` not a plain
   object → descriptive error naming the file. Output is `JSON.stringify(obj, null, 2) + '\n'`
   so a second run is byte-idempotent.
8. Per-file status. `writeHostWiring` returns `{ path, status: 'created'|'updated'|'unchanged' }`
   for every file; the commands print it, so a replaced local edit is visible rather than silent.
   No extra confirm in `init` — the files are generated copies (same rule as the sync script) and
   `init` already asked once whether to wire hosts at all.
9. `init` never fails on `ensureMcpDeps()`: a failed install is a yellow warning pointing at
   `ripple mcp-setup`; the wiring files are still written.
10. Next-steps copy says to approve the `ripple` server when Claude Code asks, and that the two
    MCP config files are machine-specific (teammates run `ripple mcp-setup`).
12. Module lives at `src/hosts.js` and is added to CLAUDE.md's `src/` structure list.
13. Extra unit scenarios: missing source `SKILL.md` under an injected `packageRoot` throws a
    descriptive error; a stale `ripple` entry is replaced; `args[0]` / `env.RIPPLE_PROJECT_ROOT`
    contain no backslashes and `resolve()` to the expected paths; importing and running
    `writeHostWiring` with `console.log` stubbed to throw proves the library-code rule.

Recommended — decided differently:

11. `.claude/commands/ripple.md` is **not** part of the wiring. Claude Code exposes the
    `ripple` skill as `/ripple` on its own, so the command file is redundant with the skill and
    is a Claude-Code-only convenience of this repo. Recorded in `feature_list.json` as a
    removal candidate rather than removed here — that is a separate decision from this bug.

Also recorded in `feature_list.json` (deferred): a committable, machine-independent config using
`cmd /c ripple mcp` per OS — rejected for now because `ripple` is a `.cmd` shim on Windows and
`bin/ripple.js`'s top-level `import 'dotenv/config'` would load the host cwd's `.env` before
`mcp/src/env.js` could `chdir`.
